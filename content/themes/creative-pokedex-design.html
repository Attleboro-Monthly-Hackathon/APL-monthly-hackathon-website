Theme: UI, data modeling, and fan creativity

Light experience

Design and build a small Pokédex-style viewer: a list (or grid) of entries and a detail view. Use a public Pokémon API for real data, or a hand-written JSON file of original creatures.

Project ideas

  1. Classic Pokédex page — Search/filter by name; click through to a detail card (sprite, types, height/weight, flavor text).
  2. Type filter gallery — Grid of sprites filtered by type chips (Fire, Water, Grass…); practice CSS layout and badges.
  3. Original creature sheet — Skip the API: invent 6–12 monsters in JSON (name, types, stats, blurb, image URL or emoji) and render a custom dex.
  4. Compare two entries — Side-by-side stats (HP, Attack, Defense…) with simple bar charts.
  5. “Who’s that Pokémon?” mini-game — Silhouette or blurred sprite; guess from multiple choice; reveal the dex entry.

Learning goals

  • Fetching and displaying structured JSON
  • List → detail navigation (or tabs/modals)
  • Visual hierarchy: name, types, art, and short description
  • Basic filtering and search

Heavy experience

Treat the Pokédex as a product design problem: memorable art direction, richer data, and interactions beyond “click a list item.” Fan-made creatures and bold visual themes are encouraged; don’t ship Nintendo assets as your own.

Project ideas

  1. Themed dex redesign — Pick a strong aesthetic (field notebook, sci-fi terminal, stained glass, museum placard) and rebuild list + detail to match; custom fonts, motion, and type-colored accents.
  2. Regional / custom dex — Invent a region: map, encounter table, and 15+ original entries with consistent type balance and evolution lines.
  3. Team builder — Search the API, add up to 6 party members, show type coverage gaps and a shareable party URL or export.
  4. Evolution explorer — Interactive chain (baby → mid → final) with animated transitions and shared base-stat comparisons.
  5. Habitat / soundboard dex — Combine species data with cries (where legally/API-available) or habitat flavor; filter by generation or color.
  6. Accessibility-first dex — Keyboard-only browsing, high contrast mode, reduced motion, and screen-reader-friendly type labels (not color alone).

Learning goals

  • Design system thinking (colors per type, card components, empty/loading/error states)
  • Client-side routing or clean multi-view state
  • Performance: don’t fetch 1000 detail endpoints at once; paginate or lazy-load
  • Crediting data sources; understanding fan work vs. official IP

Design prompts (pick one)

  • “A Pokédex found in a ruined library—yellowed pages, ink stamps, torn corners.”
  • “A lab tablet UI: monospace type, scanlines, ‘analyzing…’ states.”
  • “Kid’s sticker book: chunky type, die-cut card shapes, sticker-pack rarity labels.”
  • “Museum audio guide: calm typography, large art, short curator blurbs.”

IP & attribution

  • Prefer PokéAPI data and documented sprite sources; link to pokeapi.co in your README.
  • Original creatures avoid asset problems—great option for a library workshop.
  • Label the project fan / educational / unofficial; don’t imply Nintendo endorsement.
  • Don’t scrape shop or account pages; stick to public APIs and your own art.

Suggested session flow

  1. Agree on real API data vs. original creatures (or a mix: 3 real + 3 invented).
  2. Sketch the detail card on paper before coding (art, name, types, one paragraph, stats).
  3. Get list + detail working with placeholder styles; then commit to one visual theme.
  4. Demo: open on a phone, search one entry, and explain one design choice you made on purpose.
